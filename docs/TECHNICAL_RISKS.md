# LiveEarth 技术风险矩阵 (Technical Risks)

本文档依照项目工程规范建立，用于记录系统在硬件资源、图形渲染、多媒体流传输、合规授权等方面的技术不确定性与风险方案。

---

## 风险列表与应对方案

### TR-01: 466×466 圆形 AMOLED 高分辨率显存占用与刷新帧率

- **问题**：
  M5Stack Stopwatch 拥有 466×466 像素。全屏 16位 (RGB565) 显存单帧需占用：
  $$466 \times 466 \times 2 \approx 434.3 \text{ KB}$$
  若使用双缓冲（Double Buffering）以避免屏幕撕裂与闪烁，需要至少 **~870 KB** 连续显存，这远超 ESP32-S3 的内部 SRAM（可用通常仅 300~400 KB）。
- **影响**：
  必须将帧缓冲区（Framebuffer）分配在外部 PSRAM（Octal SPI）。由于 PSRAM 访问速度较内部 SRAM 慢，若每帧全屏刷新，可能导致 FPS 下降或总线竞争。
- **候选方案**：
  1. 全尺寸 PSRAM 8位索引调色板或压缩缓冲。
  2. 局部脏矩形（Dirty Rectangle）更新机制。
  3. 专用 3D 渲染视口：仅在中央圆形区域（例如半径 180~200 像素）分配动态缓冲，边缘 UI 静态或按需重绘。
  4. 利用 DMA 传输在后台向 CO5300 屏幕推送数据。
- **当前方案**：
  充分利用 Stopwatch 的 8MB Octal PSRAM 分配双缓冲 Canvas，并采用 DMA 推送；后续 3D 引擎针对性优化裁剪范围（剔除圆外无用像素的着色与变换计算）。
- **验证状态**：
  **IN_PROGRESS**（Phase 1 正在进行画布显存分配与刷新基准测试）。

### TR-02: 嵌入式平台实时视频流 (HLS / WebRTC / RTSP) 解码能力限制

- **问题**：
  许多公网摄像头采用 H.264/H.265 编码的 HLS (.m3u8) 或 WebRTC 协议。ESP32-S3 缺乏硬件视频解码器，纯软件解码 720p/1080p H.264 将彻底耗尽 CPU 算力且无法保证实时帧率。
- **影响**：
  直接在设备上拉取高清 HLS 流不可行。
- **候选方案**：
  1. **Snapshot 降级**：优先获取官方提供的秒级定时快照（JPEG/PNG 静态图），ESP32-S3 具备硬件 JPEG 解码能力，可轻松达到流畅刷新。
  2. **MJPEG 方案**：对于支持 MJPEG 的公共摄像头，使用分块硬件 JPEG 解码。
  3. **后端合法转码代理**：构建合规自建转码服务，将 HLS 实时转为适合 466×466 圆形屏幕的低码率 MJPEG / 动态缩略图。
- **当前方案**：
  架构上采用抽象 `CameraPlayer` 接口，第一阶段与 MVP 坚决采用 **Snapshot / 周期快照** 模式，保证 100% 稳定与流畅；严禁在未验证软解可行性前伪造流支持。
- **验证状态**：
  **IDENTIFIED**（待 Phase 8 与 Phase 9 专题验证）。

### TR-03: 数据合法性与公开源权限漂移 (Permission Drift)

- **问题**：
  公开摄像头可能因运营方策略变更、版权声明调整、防盗链机制（如 Referer 限制、动态 Token）导致授权失效或链接失效。
- **影响**：
  可能导致设备端黑屏，或者引入非合规重分发风险。
- **候选方案**：
  1. 引入自动化验证脚本，定期巡检 HTTP 状态码与图片内容有效性。
  2. 设立严格的 `REVIEW_REQUIRED` 隔离队列，所有未获明确重分发许可的摄像头禁止进入 production 分支。
  3. 客户端提供友好的离线提示状态，即使摄像头离线，地点的人文信息与地球标记仍永久可用。
- **当前方案**：
  实现严格的自动 QA 门禁，将数据分为 Candidates、Review Queue 与 Production 数据集，建立可追溯的 `evidence_url` 与 `checked_at` 制度。
- **验证状态**：
  **CONTROLLED**（已通过本阶段的数据模式与 QA 自动化工具进行控制）。

### TR-04: M5Stack Stopwatch 板型在 M5Unified 中的自动识别兼容性

- **问题**：
  M5Stack Stopwatch 较新，采用 CO5300 驱动与自定义 PMIC/IO 扩展。若 M5Unified 未能准确识别板卡枚举，可能回退到未知板型导致屏幕初始化失败。
- **影响**：
  屏幕无法点亮或触摸无反应。
- **候选方案**：
  1. 依赖 M5Unified 最新 git master 分支中的自动探测。
  2. 若探测为 fallback，使用显式 board 配置或注册 CO5300 屏幕总线参数。
- **当前方案**：
  在 `main.cpp` 中捕获 `M5.getBoard()` 并在串口详细输出检测诊断日志；若识别异常则记录明确的修复方案。
- **验证状态**：
  **IN_PROGRESS**（Phase 1 启动验证）。
